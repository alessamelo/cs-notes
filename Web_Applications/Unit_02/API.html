API

← Back to Web Applications

An API (Application Programming Interface) is a common interface that allows different systems or software components to communicate with each other.

An API can be defined as a set of subroutine definitions, protocols, and tools for building application software. It provides methods for accessing data and functionality from an application without directly using the application's user interface.

APIs make it easier for developers to use specific technologies and functionality when building applications.

Why Use an API?

Not all users or applications are the same. Some users or clients may need individual capabilities, components, or specific data from an application.

User needs and requirements are constantly changing. APIs allow applications to expose specific functionality so that different clients can use it according to their needs.

Example: Stripe

Stripe provides APIs that allow applications to integrate payment functionality without having to implement the entire payment infrastructure themselves.

API vs. Framework

A framework can contain or expose APIs, but an API is not necessarily a framework.

A framework provides a structure and reusable functionality for developing applications, while an API defines an interface through which software components can communicate or access functionality.

API Endpoints

An API is commonly based on one or more publicly exposed endpoints and a defined contract describing how requests should be made and how responses are returned.

In the last laboratory, we created a service running on port 8000.

Electrical Analogy

An API can be compared to a list of services in an electrical system, while the endpoints can be compared to the electrical outlets (enchufes) through which those services can be accessed.

Ports

A port is a logical communication endpoint used by applications and services to receive network traffic.

Common ports include:

  • 80 - commonly used for HTTP
  • 443 - commonly used for HTTPS
  • 8080 - commonly used for alternative HTTP services and development servers
  • 8000 - commonly used by development servers

A service listens on a particular port for incoming requests. Once a request arrives, the server determines which endpoint or application should handle it.

Protocols

A protocol is a set of rules that defines how systems communicate and exchange information over a network.

Authentication and Authorization

Authentication determines who a user or client is.

Authorization determines what an authenticated user or client is allowed to access or perform.

For example, logging into a bank account is authentication. Having permission to transfer money from that account is authorization.

Network Protocols

IP

IP (Internet Protocol) is responsible for addressing devices and delivering packets between networks.

A simplified process can be represented as: 

domain name → DNS → IP address → packet delivery

DNS

DNS (Domain Name System) translates human-readable domain names into IP addresses.

For example: 

server.example.com → DNS → IP address

TCP

TCP (Transmission Control Protocol) provides reliable, ordered communication between applications running on networked devices.

HTTP

HTTP (Hypertext Transfer Protocol) is an application-layer protocol used to transfer resources and information between clients and servers.

HTTPS

HTTPS is HTTP transmitted over a secure TLS connection. It provides encryption and helps protect the confidentiality and integrity of data exchanged between the client and server.

Network Layers

A simplified network model can be represented using the following layers:

  1. Application
  2. Transport
  3. Network
  4. Physical

URL and URI Structure

Consider the following example: 

https://best.server.com:8080/api/endpoints/cars?brand=FERRARI&color=RED

A URL can contain several components:

  • Protocol: HTTPS
  • Host: best.server.com
  • Port: 8080
  • Path: /api/endpoints/cars
  • Query string: ?brand=FERRARI&color=RED

More generally, a URL identifies the location of a resource and can specify the protocol, host, port, path, query string, and fragment.

The path and other components can identify a resource or endpoint on the server. A URI is a broader concept that identifies a resource, while a URL is a type of URI that also provides information about how to locate that resource.

When HTTPS is used, the HTTP communication is protected by TLS encryption.

Web APIs and Mobile Applications

A Web API provides the advantage of allowing different applications to use the same backend functionality.

For example, consider a bank that provides both a mobile application and a web application. The bank can create different interfaces for the mobile and web applications while keeping the same backend logic.

The bank does not need to rewrite the business logic for calculating an employee's salary separately for every client. Both applications can request that functionality through the same backend API.

API endpoints can communicate with backend services that access databases and perform business logic.

SOAP vs. REST

SOAP

SOAP (Simple Object Access Protocol) is a protocol for exchanging structured information between systems.

SOAP commonly uses XML as its message format and provides a formal specification for message structure and related mechanisms.

SOAP is less common in many modern public web APIs, although it is still used in some enterprise and legacy systems.

SOAP has standardized mechanisms for features such as security, including specifications such as WS-Security.

REST

REST (Representational State Transfer) is an architectural style for designing networked applications.

REST APIs commonly use HTTP and can use different representations such as JSON, XML, HTML, or other formats.

Security is not automatically provided by REST itself. Security mechanisms such as HTTPS, authentication, authorization, and token management must be implemented as part of the system.

REST Principles

Resources

Resources should be exposed through clear and understandable URIs. The URI structure should make it possible to identify the resources being accessed.

Representations

Resources can be represented using formats such as JSON or XML. These representations contain the resource's data, objects, and attributes.

Messages

REST uses HTTP methods explicitly to communicate the intended operation on a resource.

Statelessness

REST interactions are stateless. This means that the server does not store client-specific session context between individual requests as part of the REST interaction.

For example, when a client makes a request, the server processes the request using the information contained in that request and returns a response. The next request should contain the information necessary for the server to process it.

Statelessness can be beneficial because the server does not need to maintain the state of every client between requests, which can make systems easier to scale.

Question: What Application Would Not Naturally Fit a Purely Stateless Model?

Real-time applications such as chat applications often require persistent communication and server-side awareness of connections. They therefore commonly use technologies such as WebSockets rather than relying exclusively on independent REST requests.

HTTP Methods

HTTP defines several methods that indicate the intended operation of a request.

  • GET: Retrieve information or a resource.
  • POST: Submit data or request that the server perform an operation using the provided representation.
  • PUT: Create or completely replace a resource representation at a specified URI.
  • PATCH: Partially update a resource, such as modifying a specific field.
  • DELETE: Remove a resource.
  • HEAD: Retrieve the headers that would be returned for a corresponding GET request without the response body.
  • OPTIONS: Request information about the communication options supported by a resource or server.
  • TRACE: Perform a diagnostic loop-back test of the request path.
  • CONNECT: Establish a tunnel to the server, commonly used with proxies.

HTTP Status Codes

HTTP status codes are divided into five main categories:

  • 1xx - Informational: The request was received and processing is continuing.
  • 2xx - Success: The request was successfully received, understood, and processed.
  • 3xx - Redirection: Further action is required, often involving another resource or location.
  • 4xx - Client Error: The request contains an error or cannot be fulfilled due to something associated with the client.
  • 5xx - Server Error: The server failed to fulfill a valid request.

Webhooks

A webhook is an HTTP endpoint used to receive event notifications from another system.

The technical mechanism is still an HTTP request sent to an endpoint. The main distinction is semantic: a webhook is generally used when the provider sends a notification because an event occurred, rather than the client repeatedly asking whether the event has occurred.

Endpoint vs. Webhook

The HTTP mechanism is essentially the same. A webhook is an endpoint whose role in an integration contract is to receive event notifications, usually asynchronously.

Example: Payment

Suppose a customer wants to buy a monitor.

With polling, the application could repeatedly ask the payment service: "Has the customer paid for the monitor?"

It would continue asking until the payment is completed.

With a webhook, the payment service can notify the application when the customer actually completes the payment.

Example: Fast-Food System

Consider a fast-food system where a customer buys a burger. The customer receives an order number or notification mechanism.

Instead of repeatedly asking whether the burger is ready, the system can send a notification when the employees finish preparing it. The customer can then go and receive the order.

Webhook vs. WebSocket

A webhook should not be confused with a WebSocket.

A webhook is an HTTP-based mechanism for delivering event notifications to an endpoint.

A WebSocket is a communication protocol that establishes a persistent, bidirectional communication channel between a client and server.

WebSockets operate over TCP. They are useful when continuous, bidirectional, real-time communication is required.

REST APIs generally use independent HTTP request-response interactions, while WebSockets maintain an established communication connection.

Uniform Resource Locator

A URL (Uniform Resource Locator) is a formatted string used to identify and locate a resource.

A URL can contain:

  • Communication protocol
  • Host or IP address
  • Port
  • Path
  • Query string
  • Fragment

URL Components

https://example.com:8080/api/cars?brand=FERRARI#details
  • https - protocol
  • example.com - host
  • 8080 - port
  • /api/cars - path
  • ?brand=FERRARI - query string
  • #details - fragment

Ports

A port number identifies a logical communication endpoint on a host. TCP and UDP port numbers range from 0 to 65535.

Ports below 1024 are generally known as well-known ports. Ports such as 8080 and 8000 are commonly used for development or alternative application services.

Virtual Hosts

A virtual host allows a single physical or virtual server to host multiple websites or services, with requests being directed according to information such as the hostname.

RFC

RFC (Request for Comments) documents are publications used to specify and document Internet protocols, standards, and related technical information.

URL Encoding

URLs have restrictions on which characters can be used directly. Some characters have special meanings within URLs, while others must be encoded.

Characters that cannot safely be used directly in a URL can be percent-encoded using the format: 

% + hexadecimal character code

For example, a space can be encoded as %20. In the application/x-www-form-urlencoded format commonly used for query strings and HTML form data, a space can also be represented by +.

These restrictions are not only determined by the operating system. URL syntax and character restrictions are also defined by the relevant Internet standards and protocols.

PHP URL Encoding

PHP provides functions for encoding and decoding URL components: 

urlencode(string)
urldecode(string)

URL encoding is particularly relevant when values are placed inside a URL, such as query parameters.

In the last workshop, we did not have to configure URL encoding for the data sent in the request body because the information was not being placed directly in the URL.

HTML Forms and APIs

In the first workshop, when creating an HTML form, the action attribute determines where the form data should be sent.

Now that APIs and endpoints have been introduced, the action attribute can be connected to an API endpoint so that the form sends its information to the backend service. 

<form action="/api/users" method="POST">
    ...
</form>

The form can therefore send data to an endpoint, where the backend processes the submitted information.

MIME Types

MIME (Multipurpose Internet Mail Extensions) types identify the format of data being transmitted.

MIME types are widely used in email and are also important in HTTP communication.

APIs commonly use JSON for data exchange, but the format must be indicated using the appropriate content type when necessary.

For JSON, the MIME type is: 

application/json

JSON does not directly contain binary image data in the same way that an image file does. Binary data may need to be encoded, for example using Base64, or the image can be sent using an appropriate Content-Type such as image/jpeg or image/png.

Different content types can be used depending on the data being transmitted.

Query Strings

In a URL, the question mark (?) begins the query string.

For example: 

/api/cars?brand=FERRARI&color=RED

In this example, the query string contains two parameters:

  • brand = FERRARI
  • color = RED

POST Request Method

The POST HTTP method is commonly used to submit data to a server or request the creation of a resource.

Unlike GET, where parameters are commonly included in the URL, POST data is typically transmitted in the request body. The body can use different formats depending on the API, such as JSON or form-encoded data.

For example, a client can send: 

POST /api/users

Content-Type: application/json

{
    "name": "John",
    "age": 25
}

The backend receives the request, processes the submitted data, and returns an appropriate HTTP response.
