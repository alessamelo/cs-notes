Introduction to GitHub

Version Control

Version control is important because it allows us to keep track of changes made to a project.

Without version control, developers often create manual copies of their projects to keep previous versions.

With version control, we can easily search for bugs and understand how the project has changed over time.

Git is open source and scalable.

  • Git stores files and their history over time.
  • Different versions can be inspected and compared.
  • Changes can be combined.
  • Previous versions can be restored.
  • We can see who made changes.

Git and GitHub

Git is the tool that provides version control.

GitHub is a cloud-based repository platform that can be connected with Git for version control and collaboration.

GitHub is not the only platform that can be used with Git. Other platforms include GitLab and Bitbucket.

Bitbucket

Bitbucket is developed by Atlassian, the same company behind Jira. It can connect version control with project management features such as epics and branches.

Git and the Shell

Git can be used through the shell or terminal.

The shell is a program used for executing programs and commands.

Directory

A directory is a location used to organize files and other directories.

Terminal Commands

pwd

Shows the directory in which we are currently located. 

pwd

ls

Lists the files and directories in the current directory. 

ls

Changing Directory

The cd command is used to change the current directory. 

cd archive

Checking the Git Version

The Git version can be checked using: 

git --version

Git Repository

A Git repository is a directory that contains files, subdirectories and Git storage.

Git stores its extra information in a directory called .git, which is located in the repository's main directory.

Every folder that is a Git repository contains a .git directory.

The .git directory should not be modified manually. Git commands should be used to modify the repository information.

In Windows, hidden files and directories can be displayed with: 

ls -la

Do not delete or manually modify the .git directory.

Benefits of Repositories

  • Collaborate with colleagues.
  • Track changes to the project.
  • Compare different versions.
  • Return to previous versions.

Before Starting with Git

Before starting to work with Git, we can check the installed version using: 

git --version

Git User Configuration

Git needs to know the identity of the person making the commits. 

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

The current global configuration can be checked with: 

git config --global --list

The --global option applies the configuration to the user's Git configuration. Without the global option, a different identity can be configured for a specific repository.

This can be useful when different users or identities are required for different folders or repositories.

Creating a Git Repository

The command git init can be used to initialize a Git repository. 

git init mental-health-workspace

This creates a Git repository called mental-health-workspace.

An existing project can also be converted into a Git repository by running git init inside the project directory. 

git init

Checking the Repository Status

The current status of the repository can be checked with: 

git status

git status shows information about the current branch and the state of the files.

If there are files that Git is not tracking, they appear as untracked files.

Nested Repositories

A nested repository occurs when a Git repository is created inside another Git repository.

This should generally be avoided because there will be two .git directories, which can create confusion about which repository is tracking the files.

Git Mental Model

Git can be understood as a sequence of stages through which changes move before they are shared with other developers.

  1. Working Directory

    This is where we create and edit the files. 

    git add
  2. Staging Area

    The staging area contains the selected changes that are going to be included in the next commit. 

    git commit
  3. Local Repository

    The committed changes are stored in the local Git repository. 

    git push
  4. Remote Repository

    The remote repository contains shared commits and can be hosted on platforms such as GitHub, GitLab or Bitbucket.

The important distinction is that git add and git commit modify the local Git workflow, while git push sends committed changes to the remote repository.

Staging Files

Adding a File

A specific file can be added to the staging area using: 

git add file

Adding All Files

All files in the current directory can be added using: 

git add .

It is a good practice to check git status before using git add . to avoid staging unwanted changes.

Removing a File from the Staging Area

A staged file can be removed from the staging area using: 

git restore --staged file

Making a Commit

A commit changes files from the staging area into a committed version stored in the local repository. 

git commit -m "Adding"

The -m option allows us to provide the commit message directly without opening an editor.

Each commit has an identifier, a date, and information about the changes. Previous versions can be accessed through the commit history.

A good practice is to make each commit represent a coherent change and use a short message that explains its purpose.

Git History

git log --oneline

Displays a list of commits in a compact format. 

git log --oneline

The output includes the commit identifier and the commit message.

HEAD

HEAD is a pointer that indicates the current position in the commit history, normally pointing to the current branch and its latest commit.

git log

The git log command provides more information about the commit history, including who made the changes and when they were made. 

git log

git show HEAD

Shows more detailed information about the commit currently referenced by HEAD. 

git show HEAD

Visualizing the Commit History

git log --decorate --graph --all

This can be used to visualize branches and the relationships between commits.

Git Diff

The git diff command compares different states of files in a repository and shows exactly which lines have been changed, added, or removed. 

git diff

Diff can also be used to compare files or changes between different branches.

Using diff, we can inspect the differences between versions before committing or merging changes.

Git Ignore

A .gitignore file specifies files and folders that Git should not track.

This is important because a project may contain files that should not be committed, such as:

  • Secret keys.
  • Configuration files containing sensitive information.
  • Generated files.
  • APK files or other build artifacts.

Adding a secret file to Git and then deleting it from the working directory does not necessarily remove it from the repository history.

Therefore, .gitignore is also important for preventing sensitive or unnecessary files from being added in the first place.

Ignoring and Including Specific Files

Git ignore rules can be combined to ignore a folder while allowing specific files or folders inside it to be tracked. 

app/*
!app/Resources*

The ! symbol can be used to create an exception to an ignore rule.

git mv

The git mv command can perform file moving or renaming operations while also updating Git's tracking of the file. 

git mv old_name new_name

Branches

A Git branch is a pointer to a sequence of commits. Branches allow developers to work on different changes independently. 

E1 → E2 → E3 → A → B
              \
               → C → D

Branches can diverge from a common commit and later be merged together.

Renaming a Branch

The git branch -m command is used to rename a branch. 

git branch -m new-name

Creating and Switching to a Branch

The git switch -c command creates a new branch and switches to it. 

git switch -c new-branch

Branches should have intuitive names that describe the work being performed.

Merge Conflicts

A Git conflict can occur when changes from different branches affect the same part of a file and Git cannot determine automatically which changes should be maintained.

When this happens, the developer must resolve the conflict manually before the branches can be merged.

Working with Remote Repositories

git fetch

git fetch retrieves information about changes from a remote repository without directly merging those changes into the current branch. 

git fetch

Do Not Work Directly on Main

A common development practice is to avoid working directly on the main branch. Instead, developers create a separate branch for their changes.

This allows the changes to be tested and reviewed before they are incorporated into the main branch.

Pull Requests

A pull request is used to propose changes from one branch to another, usually before merging the changes into the main branch.

In an industrial development workflow, another developer or an assigned maintainer can review the changes and verify that there are no unresolved conflicts or problems before the changes are merged.

Git Workflow

A typical Git workflow can be represented as:

  1. Sync with the remote repository.
  2. Create or switch to a branch.
  3. Edit and test the project.
  4. Use status and diff to inspect changes.
  5. Stage the desired changes.
  6. Commit the changes.
  7. Push the branch to the remote repository.
  8. Review and merge the changes.
